\begin{abstract}
\noindent
Most companies today rely on automated data pipelines to collect, process, and store data for dashboards, machine learning models, and business reports. Data engineers focus on keeping pipelines running. Data quality problems are handled later by analysts or data scientists, and sometimes go undetected entirely.

Traditional quality checks in ETL pipelines are rule-based, such as checks for data types, null values, and value ranges. While these rules can find known problems, they often miss more complex issues like statistical anomalies in source data.

This thesis investigates how AutoML-based adaptive profiling can be integrated into the ingestion layer of an ETL pipeline using open-source tools. A prototype pipeline was built using Apache Airflow, dbt, AWS S3, and DuckDB, extended with a custom Python library that uses PyOD for unsupervised anomaly detection and Optuna for automated hyperparameter optimisation. The pipeline ingests hourly weather data for five cities. Controlled anomalies were injected into the data to provide ground-truth labels for evaluation.

Results show that ML-based profiling detected anomalies that rule-based checks failed to catch in this experiment. The best models achieved recall up to 100\% on stable numerical columns across all five cities, and Optuna's automated search scored higher than a pure neural architecture search baseline  in 29 of 30 evaluated settings while running 6.8$\times$ faster. Training time scales differently per algorithm: IForest scales sub-linearly ($\beta = 0.307$) while LOF scales super-linearly ($\beta = 1.175$), so algorithm choice is the dominant factor in pipeline overhead.
\end{abstract}

\section{Introduction}\label{sec:introduction}
% ============================================================

In university, students typically download a static CSV file and run analysis on it. In the real world, data is produced every millisecond. Companies collect it continuously from sensors, APIs, user interactions, and external providers. They rely on it to power dashboards and make business decisions. To keep all this data updated and usable, engineers build automated systems called data pipelines that decide where to collect data, how to process it, and where to store it.

The most common type is the ETL pipeline: Extract, Transform, Load. Data is pulled from a source called upstream, processed and transformed, applies aggregations, and then written to a data warehouse where analysts and downstream users can use it.

The problem is that traditional quality checks inside ETL pipelines are rule-based. A data engineer writes checks like ``temperature must not be null'' or ``pressure must be integer type between 870 and 1085 hPa.'' These rules work well for obvious errors, but they only catch problems the engineer already knew about. Statistical anomalies, gradual sensor drift, or unexpected value distributions will pass through rule checks without triggering any alert \cite{Maddali2021AutomatingDQ, taleb2016dqrules}.

This thesis investigates whether machine learning can fill that gap. Instead of fixed rules, a model learns what normal data looks like from historical data and flags anything that deviates from that learned pattern. The goal is to make this automatic: no manual rule writing, and minimal domain expertise required for individual columns.

\subsection{Motivation and Practical Relevance}

Rule-based quality checks exist, but subtle anomalies still pass through pipelines unnoticed. Quality checks are often applied after data has already been processed, so problems reach analytics and models before anyone spots them.

Recent industry work \cite{databricks2025aietl} shows that AI-driven ETL systems can automatically learn what normal data looks like and detect deviations before they reach downstream systems. Problems get caught earlier, before they propagate.

One main motivation is the idea of ``shift-left'' data quality: validate data as early as possible in the pipeline, ideally at ingestion \cite{datakitchen2023shiftleft}. If a bad record enters at ingestion, every transformation after that inherits the problem. Without early validation, each downstream team finds and fixes the same issue independently.

The other motivation is to reduce the cost of computation for high-quality data delivery by applying outlier detection once, rather than repeatedly by different downstream users. In practice, many data teams skip anomaly detection entirely due to the cost of engineering and human resources required.

\subsection{Research Questions}

The main research question is:

\begin{center}
\emph{How effective and practical is ML-based anomaly detection for data quality monitoring in ETL pipelines?}
\end{center}

This is explored through two sub-questions:

\begin{itemize}
  \item How accurately can ML-based anomaly detection detect data quality issues compared to rule-based checks?
  \item What is the impact of integrating anomaly detection into the ingestion stage on pipeline performance, resource usage, and operational monitoring?
\end{itemize}

\section{Background}\label{sec:background}
% ============================================================

\subsection{Data Pipelines in Practice}

A data pipeline is the system that handles this automatically. There are two main types. Real-time pipelines process data as it arrives, suitable for fraud detection or live dashboards. ETL pipelines process data in batches on a schedule, suitable for analytics, reporting, and training machine learning models.

\subsubsection{Business Use of ETL Pipelines}

ETL pipelines are central to how data-driven companies operate. A travel platform such as Skyscanner might collect different types of data that affect flight pricing, for example:

\begin{itemize}
  \item Data from booking platforms such as Booking.com to identify demand based on hotel reservations.
  \item Data from airlines such as KLM and Lufthansa to adjust pricing and identify travel seasons.
  \item Data from weather services to predict when people are more likely to travel to destinations with optimal weather.
\end{itemize}

This data can be used to adjust prices based on demand, helping the company remain profitable, stay competitive in the market, and offer customer-friendly prices. This process can be automated through data pipelines.

In each case, the pipeline extracts raw data from sources the company does not control, transforms it into a consistent and usable format, and loads it into a warehouse that supports products and business decisions. The quality of everything downstream depends directly on the quality of the data that flows through the pipeline.

\subsubsection{ETL: Extract, Transform, Load}

\textbf{Extract} pulls data from a source: a REST API, a database like PostgreSQL, Datalakes, or a stream. In this project, data is extracted from the Open-Meteo weather API to simulate a modern ETL system.

\textbf{Transform} reshapes and cleans the data: fixing types, removing duplicates, joining tables and running quality checks. In this pipeline, transformation is handled by dbt, which runs SQL on a DuckDB warehouse.

\textbf{Load} writes the processed data to its destination. Here the data is stored as Parquet files on Amazon S3, and transformed results are materialized as tables in DuckDB/MotherDuck.

\subsection{Data Quality in ETL Pipelines}

Data quality problems in ETL pipelines are common. Sources change their schemas, sensors send wrong readings, APIs return corrupted records, and values drift outside expected ranges over time. When these problems go undetected, they propagate through the pipeline into every downstream system.

Chu et al. \cite{chu2016datacleaning} describe two types of data quality problems. Qualitative problems are violations of integrity constraints such as wrong types, missing values, or uniqueness failures. Quantitative problems are statistical anomalies that are technically valid values but unusual compared to what the data normally looks like. Rule-based checks address the first type well, but cannot address the second.

Sculley et al. \cite{sculley2015hidden} showed that hidden technical debt in ML systems often comes from the data pipeline. When data quality is not monitored at the source, every downstream system inherits the problem.

\subsection{The Case for Shift-Left Data Quality}

``Shift-left'' means validating data as early as possible in the pipeline, ideally at the point of ingestion. If a bad record enters the pipeline at ingestion, it passes through every transformation after that. By the time it reaches an aggregated report or a trained model, it may be impossible to identify which source record caused the problem.

Detecting the problem at ingestion stops this propagation immediately. The flagged record can be excluded from downstream processing before it reaches any consumer. This is the core argument for integrating anomaly detection into the ingestion layer rather than leaving it to downstream users \cite{datakitchen2023shiftleft, krishnan2016activeclean}.

\subsection{Unsupervised Anomaly Detection}

Unsupervised anomaly detection identifies unusual data points without labelled training data. The idea is to train a model on historical data to learn what normal looks like, then score new records based on how well they fit that learned distribution. Records that deviate significantly get a high anomaly score.


In this work, PyOD library was selected for AutoML-based unsupervised anomaly detection over H2O AutoML, AutoGluon and PyCaret because of its targeted models for this task and simplicity of integration into the proposed ``Adaptive Profiling'' library.

Four algorithms from the PyOD library \cite{zhao2019pyod} were selected by Optuna across all trained models in this project:

\textbf{Local Outlier Factor (LOF)} measures the local density of a point compared to its neighbours. Points in relatively sparse local regions get high anomaly scores. It is effective for contextual anomalies and scales super-linearly with data size.

\textbf{ECOD (Empirical Cumulative Distribution-based Outlier Detection)} estimates the tail probability of each feature using the empirical distribution. It is fast, interpretable, and essentially parameter-free, making it a strong baseline for univariate columns with tight distributions.

\textbf{Histogram-based Outlier Score (HBOS)} estimates the density of each feature independently using histograms. It is fast and effective for low-dimensional data where features are approximately independent.

\textbf{COPOD (Copula-based Outlier Detection)} uses empirical copula functions to model the joint distribution of features and scores outliers by their tail probability. It is fast and parameter-free.

Campos et al. \cite{campos2016evaluation} show that no single algorithm dominates across all datasets. The right choice depends on the data, which is why automated model selection is important.

\subsection{AutoML and Hyperparameter Optimisation}

AutoML refers to automating the selection of algorithms and their hyperparameters. Instead of manually choosing between Isolation Forest, LOF, OCSVM and ECOD, and tuning each model by hand, an optimisation framework searches the possible configurations automatically.

Optuna is used for this purpose and selected over Scikit-Optimize (skopt), Hyperopt and Ray Tune because it is simple to use, compatible with PyOD, and well suited for searching across model types and key hyperparameters.

\section{Related Work}\label{sec:relatedwork}
% ============================================================

\subsection{ML-Based Quality in ETL Pipelines}

Several recent studies have integrated machine learning into ETL data quality. Maddali \cite{Maddali2021AutomatingDQ} describe an ML-based quality system for ETL that automates detection without manual rule configuration. Raghu Gopa \cite{gopa2025aiaugmentedetl} show that AI-augmented ETL pipelines can detect anomalies and enforce data governance automatically at ingestion.

What makes this work novel is the integration of AutoML based on historical data, which helps automate the tuning and retraining of models when data patterns change. This reduces the need for continuous engineering effort and lowers the cost of maintaining quality checks. In many teams, data engineers may not have the required machine learning domain knowledge, while close collaboration with data scientists can be difficult and costly. As a result, companies often continue to rely on rule-based quality checks and may overlook important failure points in the data.

\subsection{Limitations of similar tools}

The SIGMOD 2016 tutorial by Chu et al. \cite{chu2016datacleaning} draws a clear distinction between qualitative and quantitative data quality problems and shows that modern systems need both approaches. Rule-based systems like Deequ \cite{schelter2018automating} handle qualitative problems well but cannot detect statistical anomalies. A group of researchers \cite{taleb2016dqrules} document that rule-based systems require significant manual effort and systematically fail on anomalies that do not violate any written rule.

\subsection{Cost of Late-Stage Cleaning}

ActiveClean \cite{krishnan2016activeclean} shows that dirty data systematically biases downstream model parameters, and that cleaning earlier in the pipeline gives up to 2.5 times better model accuracy for the same cleaning budget. HoloClean \cite{rekatsinas2017holoclean} shows the broader trend away from pure rule-based quality toward learning-based approaches.

\subsection{AutoML for Anomaly Detection}

Koh et al. \cite{KOH2022107886} demonstrate AutoML applied end-to-end in an industrial domain, showing that an automated pipeline generalises across different dataset configurations without manual tuning. Emmott et al. \cite{emmott2013systematic} provide a methodology for constructing ground-truth anomaly detection benchmarks by injecting controlled anomalies, which is the evaluation approach used in this project.

\subsection{Classical ML vs.\ Neural Networks for Tabular Anomaly Detection}
\label{sec:relwork_nn}

For high-dimensional inputs like images or audio, neural autoencoders are a natural fit for anomaly detection, however this logic does not carry over to low-dimensional tabular data. A single-column input gives the autoencoder nothing meaningful to compress. A network with even a few hidden layers can memorise the training set, so reconstruction error does not reliably separate anomalies from normal points.

Campos et al.\ \cite{campos2016evaluation} evaluate nineteen unsupervised detectors on a large benchmark and find that density-based algorithms such as LOF consistently outperform more complex alternatives on low-dimensional tabular data. Zhao et al.\ \cite{zhao2019pyod} confirm the same finding in the PyOD benchmark: classical algorithms are competitive with or better than deep learning models on tabular tasks, and they require substantially less compute.

Speed is also a practical concern. Training a neural network for tens to hundreds of epochs per Optuna trial is much more expensive than fitting a tree or density model. Section~\ref{sec:autonn_comparison} reports a direct comparison: classical AutoML achieves 4.1$\times$ higher mean F2-score at 6.9$\times$ lower search cost per column.

\subsection{The Adaptive Profiler Library}

Quality checking in this pipeline has two layers.

The first layer is \textbf{rule-based}. Every column has an expected type, a valid range, and a not-null constraint. These rules form a data contract: a written agreement about what the data should look like. dbt enforces a similar contract at the transformation layer through schema tests on the warehouse models. Both rule sets run on every incoming batch and flag any record that violates a constraint.

Rule-based checks are fast and transparent, but limited. A rule like \texttt{range: [-10, 60]} for temperature in Celsius will not catch a sensor reading of 0°C when every other reading in the past three days was above 25°C.

The second layer is \textbf{ML-based}. For any column marked \texttt{automl: true} in the configuration, a statistical model is trained on recent historical data. The model learns what normal looks like for that column and flags values that fall outside its learned distribution, even when they pass all rule-based checks. This is what the library calls adaptive profiling.

Both layers are declared in a single YAML configuration file. An example is shown below.

\newpage

\begin{lstlisting}[language=yaml, caption={Example \texttt{profiling\_schema.yml}. Each column declares a type and rule-based checks (data contract layer) and optionally enables an AutoML model (\texttt{automl: true}).}]
# Where trained models are saved
model_store:
  backend: s3
  bucket: weather-etl-bucket

In \textbf{training mode}, Optuna searches for the best model and hyperparameters for each configured column. Trained models are saved to S3 under a path that includes the column name and city, so Amsterdam gets its own model trained on Amsterdam's weather patterns.

In \textbf{scoring mode}, the profiler loads the saved model for each column and scores new incoming rows. The output is a long-format DataFrame with one row per (timestamp, column) containing the anomaly score, a binary flag, and any rule-based violations. Failures are reported in the output rather than raised as exceptions so the pipeline keeps running.

\subsection{Training on Recent Batches}

In real-world ETL pipelines, historical data can span years or even decades, making it impractical to retrain on the full history every time. Loading millions of rows just to update an anomaly detection model would be too slow and too expensive for a daily pipeline, so the system trains on recent batches instead. Only the most recent window of data is used, and this window can be configured through the Adaptive Profiling library.

This keeps training fast and computation manageable while still giving the model enough data to learn stable patterns. It also allows the model to adapt over time: if a data source gradually shifts due to seasonal change, sensor recalibration, or a source system update, the next scheduled retraining picks up the new pattern automatically.

\subsection{Dataset}

The experiments use weather data from the Open-Meteo API, benchmarked across five different cities: Amsterdam, New York, London, Paris, and Tokyo. Each hourly record contains temperature, apparent temperature, precipitation, surface pressure, soil temperature, and soil moisture. The data is stored in Parquet format on Amazon S3. Each city dataset contains approximately 20,856 hourly records.

Weather data was selected for this work because it is widely used by businesses to improve planning, prediction, and service optimisation. For example:
\begin{itemize}
  \item \textbf{TomTom/Google Maps:} Weather conditions can be compared with historical traffic patterns to improve traffic estimation systems.
  \item \textbf{UPS/FedEx/Amazon:} Delivery delays can be compared with weather conditions to improve route planning, ETA prediction, and driver scheduling.
  \item \textbf{Uber/Bolt:} Weather effects on ride demand, cancellations, pickup delays, and surge pricing can be analysed.
  \item Many other businesses ingest weather data to improve pricing, operations, and service optimisation.
\end{itemize}


\subsection{Experiment Design}

The two research sub-questions map to two main experiments, with one additional validation experiment comparing the chosen classical AutoML approach to a neural architecture search alternative.

\textbf{Experiment 1: Detection effectiveness.} To answer how accurately ML-based detection finds data quality issues compared to rule-based checks, controlled anomalies are injected into the data and the system's detections are compared against the known injection labels. This directly measures detection quality.

\textbf{Experiment 2: Practical overhead.} To answer the practical impact question, a built-in projection tool in the profiling library benchmarks training time across different data sizes, column counts, trial budgets, and hardware configurations, and fits an empirical scaling law to the results.

\subsubsection{Experiment 1: Anomaly Injection and Detection}

A randomly selected subset of records (approximately 0.36\%, around 76 records per city) has one column's value shifted by a controlled amount. The injected records serve as ground-truth labels.

Model performance is measured with precision, recall, F1-score, and F2-score. F2 weights recall more heavily than precision. Missing a real anomaly is considered worse than a false alarm.

\subsubsection{Experiment 2: Scaling and Cost Projection}

The projection tool runs the full training pipeline across approximately 90 benchmark configurations, varying data size, column count, and Optuna trial budget. Results are fitted to an empirical power-law scaling model:

$$T(n, m, k) = \alpha \cdot n^{\beta} \cdot m^{\delta} \cdot k^{\gamma}$$

where $n$ is the number of rows, $m$ the number of columns, and $k$ the number of Optuna trials. Once fitted, the formula predicts training time for any configuration. Run it on a small sample, get an estimated time for the full dataset, and decide whether the overhead is acceptable before setting up production.

This parameters are given by the Adaptive Profiling library by embedded experiment feature to have an estimation over projection to larger scale data and possibility of using on different set of metrics and pipelines.

\subsubsection{Discussion of Amsterdam Results}
\label{ssub:amsterdam_results}

\textbf{Column characteristics determine performance.} Surface pressure and soil columns have tight, predictable distributions, so even small shifts are statistically unusual. \textbf{When AutoML is not the right choice.} Figure~\ref{fig:ams_precipitation} shows Amsterdam precipitation which follows a heavily right-skewed distribution: most hours record zero rain, and the hours that do have rainfall are highly variable with no stable seasonal shape. A model trained on this column had difficulty distinguishing an injected anomaly from a naturally extreme value in this dataset, which explains the consistently low F2 scores for precipitation across all five cities in these experiments. Columns with this kind of distribution may not be good candidates for ML-based anomaly detection. Running the profiling pipeline on a data sample before production deployment lets a data engineer identify these columns early and set \texttt{automl: false} for them rather than spending trials on a model that is unlikely to converge to a useful threshold.

\subsection{Experiment 2: Practical Overhead and Scaling}

The second experiment answers the second research sub-question: is ML-based profiling practical in terms of pipeline overhead and resource usage?

A built-in projection tool in the profiling library benchmarks training time across different data sizes, column counts, and trial budgets, then fits an empirical scaling law to the results. It was run across approximately 90 benchmark configurations on the same hardware used for production. This tool lets any user predict how long training will take at their full data scale before committing to a deployment.

\subsubsection{The Scaling Formula}

The formula is inspired by work in ML research showing that training behaviour follows power laws. Kaplan et al.\ \cite{kaplan2020scalinglawsneurallanguage} showed that for large language models, performance scales predictably with data size, model size, and compute. Each factor contributes independently, so they can be multiplied together. The result has the shape: \emph{performance = constant $\times$ (data size)$^\text{exponent}$ $\times$ (model size)$^\text{exponent}$}. Bordelon et al.\ \cite{pmlr-v235-bordelon24a} later showed theoretically that training time, data size, and model size each carry their own power-law exponent, and those exponents can differ from each other.

The formula uses the same structure where inputs are rows ($n$), columns ($m$), and Optuna trials ($k$). Hardware power directly affect the $\alpha$ constant across all benchmark runs. The fitted formula is:

$$T(n,\, m,\, k) \;=\; \alpha \cdot n^{\,\beta} \cdot m^{\,\delta} \cdot k^{\,\gamma}$$

Table~\ref{tab:scaling_params} explains what each symbol means and where its value comes from.

\begin{table}[H]

\midrule

$m$      & Columns           & Number of features to be profiled having \texttt{automl: true} \\
$k$      & Trials            & Amount of models and parameters Optuna tries \\
\midrule
$\alpha$ & Baseline constant & Fitted from benchmark runs which correlates with the hardware\\
$\beta$  & Row exponent      & Fitted by benchmarking at different row counts \\

\bottomrule
\end{tabularx}
\end{center}
\caption{Inputs and fitted parameters. $n$, $m$, $k$ are known at runtime. The exponents $\beta$, $\delta$, $\gamma$ are hardware-independent and describe how time scales with each factor. $\alpha$ is hardware-dependent and was fitted on the benchmark machine.}

The exponents $\beta$, $\delta$, $\gamma$ are properties of the algorithms and data structure where they do not change with hardware. Only $\alpha$ changes if the experiment runs on a different machine. All four values can only be obtained by running the projection tool across different configurations and measuring real training times.

\subsection{Experiment 3: AutoML vs.\ Neural Architecture Search}\label{sec:autonn_comparison}

To validate the choice of classical PyOD algorithms over neural network detectors, both approaches were run on the same five-city dataset, same preprocessing, and same unsupervised objective. Neither sees anomaly labels at any point.

\begin{itemize}
  \item \textbf{AutoML:} Optuna selects among IForest, LOF, ECOD, HBOS, and COPOD with 25 trials per column.
  \item \textbf{Auto-NN:} Optuna performs neural architecture search (NAS) purely over neural network models --- Autoencoder (AE) and Variational Autoencoder (VAE) --- varying hidden layer count, width, activation function, learning rate, epoch count, and batch size, with 25 trials per column (matching AutoML for a direct comparison). One-Class SVM is intentionally excluded because it is not a neural network.
\end{itemize}

The results confirm that AutoML outperforms neural architecture search in 29 of 30 univariate cases as for every other column, LOF and ECOD are structurally better suited. They compare each point to its local neighbourhood or tail probability rather than learning a global reconstruction mapping, which is exactly what is needed to detect point anomalies embedded in seasonal patterns. On top of the quality advantage, AutoML is 6.8$\times$ faster on the same trial budget, making it the unambiguous practical choice for tabular ETL anomaly detection.

\subsection{Limitations of the Evaluation}

The evaluation relies on synthetically injected anomalies. Real data quality problems may look different: they may be sustained drift rather than point anomalies, or they may affect multiple columns at once.

All experiments use weather data, which has strong seasonal patterns and relatively stable distributions. The approach may behave differently on other types of data such as financial transactions or IoT sensor streams with abrupt regime changes.

If anomalies already exist in the historical training data, the model will learn to treat them as normal. This is a fundamental limitation of unsupervised learning.

The approach trains one model per column independently. Anomalies that only appear as correlated shifts across multiple columns simultaneously would not be detected by this design.

\section{Conclusions and Further Research}\label{sec:conclusions}
% ============================================================

\subsection{Conclusions}

The main question was whether ML-based anomaly detection can be added to an ETL ingestion layer practically, and whether it catches more problems than rule-based checks.

On \textbf{detection}: ML-based profiling caught anomalies that rule-based checks failed to detect. For stable columns like surface pressure and soil moisture, recall reached 94--100\% across all five cities. For noisier columns like temperature, recall was 67--79\% in the better-performing cities. Rule-based checks scored 0\% on the same injected anomalies. Automated model selection with Optuna scored higher than a pure neural architecture search baseline while running 6.8$\times$ faster. LOF was selected most often. ECOD won on surface pressure in 4 out of 5 cities, demonstrating particularly efficient performance on columns with tight, predictable distributions.

On \textbf{overhead}: The system runs as a working pipeline on AWS. Adding the ML detection step to the Airflow DAG required few changes. The built functional Adaptive Profiling library, help users to evaluate whether this framework fits their usecase and cost worthy or not based on their data. One time training or scheduled batch training is now simple possible by a a single line configuration on any column. 

On \textbf{shift-left}: Catching anomalies at ingestion stops bad data before it reaches any downstream transformation or report. Fixing problems at the source is cheaper than cleaning them up later.

The most important practical conclusion is that rule-based and ML-based checks are complementary. Rules handle obvious violations quickly and interpretably. ML-based detection adds a statistical layer for subtle anomalies that no rule would catch.

\subsection{Further Research}

Testing on datasets from different domains (finance, IoT, e-commerce) would show how well the approach generalises beyond weather data.

The evaluation used point anomalies in individual columns. Extending the system to detect joint anomalies (shifts that only appear as correlations across multiple columns) would broaden its applicability.

The current system trains on a schedule and reuses the model until the next retraining. Adding automatic drift detection and retraining triggers when distribution shift is detected would make the system more robust in production.

Adding explanations for why a record was flagged upon upstream source elaboration would help operators understand and improve monitoring systems.
